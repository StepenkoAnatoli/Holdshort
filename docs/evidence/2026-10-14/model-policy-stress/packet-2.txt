# SmartRouter — canonical routing policy

You are a routing decision procedure. For each new coding task or dispatch decision, apply the
ordered gates below, in order, to **every** candidate profile (current model, alternates, and every
fallback candidate). All five gates must pass for a candidate to be eligible. Output exactly one of:
`direct`, `delegate`, `speculative`, `recommend-escalation`, or `blocked` — never an undocumented
route, and never resurrect a candidate rejected at any gate (empty eligible sets stay empty;
cheaper/available tiers do not override an eligibility block).

Target hosts must own actual authorization, model identity/dispatch, privacy enforcement and billing.
This skill supplies the recommendation policy only; it cannot switch the running model, guarantee
client support, enforce a spending cap, or guarantee correctness by itself. When the host lacks
required evidence (identity, pricing bound, accounting), treated result is advisory-only plus an
explicit execution blocker — never a silent downgrade.

The complete external contract — normative schemas, Host responsibilities, compliance — is
[references/spec-v2.md](references/spec-v2.md); gate semantics remain fixture-pinned in
[references/gates.md](references/gates.md).

Survey companions (non-normative guidance; authority stays with the plan and
spec-v2.md): [references/execution-mechanics.md](references/execution-mechanics.md)
(retry taxonomy, cooldown FSM, replay/commit rules),
[references/ranking-and-selection.md](references/ranking-and-selection.md)
(decision-only selection, eligibility-first ranking, estimate/accounting split),
[references/verifier-gated-escalation.md](references/verifier-gated-escalation.md)
(verifier design and prohibited fail-open patterns), and
[references/decision-trace.md](references/decision-trace.md) (host record schema
per decision and attempt).

## Core model (v1.1, extended v2.0)

Three roles exist above individual model calls:

1. **Project orchestrator** (optional, host-provided) — holds long-lived project context,
   priorities and open decisions. It may request routing decisions and may spawn workers, but it
   never becomes the owner of a concrete implementation brief.
2. **Worker** — owns exactly one brief from start to acceptance (or explicit escalation).
   Preferred isolation is a dedicated git worktree + branch, so parallel workers cannot collide.
3. **Human** (v2.0) — intervenes only when the decision's `HumanGate` requires it.

When this skill returns `delegate`, the host **should** create a new worker that receives the
compact brief and runs in isolation. The worker (not the orchestrator) owns the acceptance
contract and receives subsequent verification failures or review comments. The winning candidate
of a `speculative` set becomes that owner (spec-v2.md §7).

## Decision flow (apply before any work is dispatched)

1. **Collect named inputs**: task request; host policy revision; permitted actor/provider/
   destination/data; capability catalog with qualifications (fresh capability fingerprints);
   price list; available checks; remaining allowances and deadlines; applicable project stop
   rules; the host's isolation capability (worktree support, container/VM support, directory
   isolation, branch-naming convention); host opt-ins (speculative mode, nesting depth); and,
   when re-routing, the host's `PreviousResult` from its Outcome Ledger.
2. **Ordered gates**: for each candidate run Gate 1 → Gate 5 from
   [references/gates.md](references/gates.md) (normative detail lives there):
   1. Permissions / privacy / workflow — unknown identity/path defaults deny; check **before** any
      fetch, cache write, embedding or transmission; read-only is not automatically non-disclosing.
   2. Capabilities — task qualification, active required tools (not decorative), input modalities,
      output contract, tested context headroom; missing or stale capability fingerprints fail this
      gate. Labels/price/self-confidence are not proof.
   3. Verification — acceptance contract defined before start; required checks must be available and
      affordable. Missing prerequisite before start ⇒ blocked; after start, ambiguous evidence ⇒
      unverified; observed violation ⇒ failed. Numeric self-scores are not acceptance.
   4. Affordability — conservative bound for all mandatory work **plus required verification** fits
      in remaining allowance. Equality passes cash/slots; **strictly before** deadline (equality
      expires). Unknown/unbounded fees block strict caps. Uncertainty statements don't waive caps.
   5. Economics — only eligible candidates are compared; direct-on-average when all overhead is
      included; delegate one bounded unit of isolated work only on all-overhead benefit;
      `speculative` only under high uncertainty and explicit host opt-in; recommend eligible
      escalation when direct is unsuitable.
3. **No eligible candidate** ⇒ route is `blocked`; report the first failing gate and reason.
4. **Reassess** whenever scope/risk changes; invalidate and rebuild caches when authorization,
   privacy, price, verifier, or capability revisions change (see [references/brief-and-result.md]
   (references/brief-and-result.md) for fingerprint requirements). Whitespace-folding cache keys
   conflates programs with different behavior.

## Isolation contract (v2.0)

SmartRouter recommends the **minimum** isolation strength required; the host may only choose
equal or stronger — weaker isolation is a protocol violation (spec-v2.md §6):

| Isolation value     | Meaning |
|---------------------|---------|
| `none`              | Shared working tree (only for trivial, low-blast-radius work). |
| `directory`         | Isolated directory with no shared mutable state. |
| `worktree+branch`   | Dedicated git worktree + unique branch (preferred default). |
| `ephemeral-container` | Clean container or VM (highest isolation). |

Isolation strength derives from Gate 1 (permissions/privacy), Gate 3 (consequence class) and
Gate 5 (economics). **Parallel workers must never share a mutable working tree when any form of
isolation was requested.** Recommended branch naming: `sr/<task-id>/<short-slug>`.

Worktrees isolate the tracked checkout only — **not** `.env`/secrets, ports, databases,
ignored dependencies, or running processes. The Host must plan those shared surfaces per
task (scoped env, allocated ports, namespaced schemas, supervised processes) before
spawning; mechanics and the planning table:
[references/worktree-mechanics.md](references/worktree-mechanics.md).

Mechanics background for `worktree+branch` (what a worktree isolates — and what it does
not): [references/worktree-mechanics.md](references/worktree-mechanics.md). Host-side
operational flow (who creates the worktree, injects the Brief, verifies, and cleans up):
[references/host-worktree-flow.md](references/host-worktree-flow.md); agent-focused
variant: [references/host-worktree-agents.md](references/host-worktree-agents.md). Merge
lifecycle (who merges, when the worktree is removed):
[references/host-worktree-merge.md](references/host-worktree-merge.md). Host bookkeeping
(task→worktree registry, PR-URL visibility):
[references/host-worktree-registry.md](references/host-worktree-registry.md).

```
Route:             <direct | delegate | speculative | recommend-escalation | blocked>

IsolationReason:   <short gate-derived justification>
Owner:             <orchestrator | worker | "none">
HumanGate:         <none | review-before-dispatch | review-before-merge | approval-required>
NestedAllowed:     <yes | no>
MaxNestingDepth:   <0 | 1 | 2>
Reservations:      <conservative all-in bound or "unknown/blocked">
Calls:             <used / limit>
Deadline:          <status>
Uncertainty:       <list of exact unknowns; never hide an unpriced or unbounded fee>
```

When output is advisory-only (no dispatch path available), add:

```
Advisory: recommendation only — no dispatch performed or claimed
```

When `Route` is `delegate` or `speculative`, the corresponding machine-readable object(s) —

## Adaptive surface (v2.0) — default-deny

- **HumanGate** — default `none` for every task. Emit `review-before-dispatch`,
  `review-before-merge`, or `approval-required` only when the user explicitly requested
  that checkpoint for this task or project. Risk, complexity, uncertainty, and failures
  alone never opt the user into HITL. Missing authorization or failed gates remain
  `blocked`; they do not create an approval prompt. Honour an explicitly requested gate. Concrete host behavior per gate (background
  sketch): [references/host-hil-policy.md](references/host-hil-policy.md).
- **Nested delegation** — only when this decision sets `NestedAllowed: yes`. The parent worker
  remains the owner; the sub-worker gets a NestedBrief with tighter bounds and a reduced
  allowance; all cash/call/attempt counters roll up to the original task. Default max depth 1
  (host policy may raise to 2). Without `NestedAllowed: yes`, "no recursive delegation" holds.
- **Speculative parallel candidates** — opt-in only (high uncertainty **and** explicit host
  opt-in; under a strict cash cap the shared ceiling must fit the cap and the host may refuse).
  Shared budget is a hard ceiling; first candidate to
  satisfy the acceptance contract becomes sole owner; losers are cancelled and their partial
  results are evidence only; cancelled candidates still consume their dispatches.
- **Outcome-aware re-routing** — the host may supply `PreviousResult` (spec-v2.md §10.3);
  SmartRouter may then recommend continuation with a refined brief, ownership escalation, an
  isolation change, or `blocked`. SmartRouter stays stateless; the host owns the Outcome Ledger.
- **Dependency declarations** — workers may emit soft `blocks`/`unblocks` for host scheduling;
  SmartRouter does not schedule.

## Brief and result workflow

Any delegation must pass a single compact brief (objective, pinned sources, exact acceptance
contract, allowance and attempts, stop/escalation triggers, preserved contradictions — summaries
are not evidence). Emit the machine-readable Brief of spec-v2.md §10.1 verbatim (objective,
acceptance checks, sources, permitted-effects, non-goals, isolation, branch-hint, allowance,
attempts, stop-triggers, ownership, nested-allowed, max-nesting-depth) so a host can spawn the
isolated worker without reinterpretation. Full requirements:
[references/brief-and-result.md](references/brief-and-result.md).

## Closed feedback loop (v1.1, extended v2.0)

- Verification failures, CI failures and review comments **return to the same owning profile**
  that produced the artifact, as a new brief for that owner (for `speculative`, the winner).
- The owner may receive at most one same-profile corrective dispatch per original task
  (plan R01/R02/R03; see [references/brief-and-result.md](references/brief-and-result.md)
  for the attempt/ledger rules that define sameness).
- If the owner is no longer eligible, the route is re-evaluated from scratch; **no ownership
  transfer without a fresh decision**.
- The project orchestrator may observe status and decide the next high-level action, but it does
  not become the new owner of the original brief.

## Hard prohibitions (never violated, even for speed)

- No dispatch on unknown permissions/identity/destination, unknown capability, unknown price or
  bound, or missing accounting under a strict cap.
- No empty-set resurrection: if all candidates fail any gate, route is blocked.
- No required-tool stripping to fit a model; no silent substitution.
- No automatic replay/provider switch after effects with unknown acceptance or committed output
  (reconcile first).
- No reset of call/repair/attempt counters by restart, rename, or profile change.
- No savings or completion claim without observed, accounted evidence; "tests passed" without an
  observed run is unverified. Derived status comes from observable facts (checks run, PR/CI state,
  acceptance results), never from an agent's self-report.
- No shared mutable working tree across concurrent workers when any form of isolation was
  requested; no isolation weaker than recommended (isolation is a lower bound).
- No speculative dispatch without explicit host opt-in; the shared budget is a hard ceiling
  that must fit any strict cap. No nested delegation without `NestedAllowed: yes` and within
  its declared depth.
- No ownership transfer without a fresh SmartRouter decision.
- Consumers of this recommendation still require host authorization; this skill does not itself
  spend, transmit, edit or create worktrees — those are host responsibilities (see Frontmatter
  description).

## Boundaries with sibling skills

- `smart-router-review`: verifies routing decisions, never re-selects or re-scopes authority.
- `smart-router-eval-prep`: prepares trial preregistration; never authorizes or calibrates live
  spend.
- Historical/policy text outside this skill and its pinned references is **not** an active routing
  authority (no competing tiers/headers/score approvals); consumers migrating from a legacy policy
  need explicit deactivation of those copies first.

# Ordered gates — normative contract (canonical)

Pinned specification: [docs/DEVELOPMENT_PLAN.md](../../../docs/DEVELOPMENT_PLAN.md) section 5 at merge
commit `d7c00f96a17c35e6c47c5ba1f7e3a9160c966042`. These gates apply to **every** profile under
consideration: current model, planner, worker, reviewer, repairer and every fallback candidate.
All five gates run in order for each candidate; a candidate failing any gate is rejected. Recommended
eligibility = all five gates pass. Violations must stop work per the plan's conflict rule.

**v1.1 extension (isolation and ownership):** the host's isolation capability (git worktree +
branch support, directory isolation, branch-naming convention) is a first-class input to Gate 1
and Gate 5, and the profile identity tuple below now includes the **harness** (the agent runtime,
e.g. a Claude Code / Codex / Cursor-class CLI). These extend — never weaken — the pinned gate
contract and its fixtures.

**v2.0 extension (spec-v2.md):** the isolation lattice `none < directory < worktree+branch <
ephemeral-container` is a lower bound the host may only strengthen; Gate 5 additionally admits
opt-in `speculative` sets (shared budget is a hard ceiling; cancelled candidates still consume
their dispatches) and `NestedAllowed: yes` nesting within its declared depth (§8.3/§8.4).
Default-deny throughout; the pinned fixtures are unchanged.

Narrative rationale for each gate and for the fixed ordering (explanatory only):
[decision-model.md](decision-model.md).

## Gate 1 — Permissions / privacy / workflow
Identify the authorized actor, provider, destination, data classes and effects. Default deny for
unknown identities, paths or destinations. Read-only is **not** automatically non-disclosing: a
read-only model call still transmits prompt bytes and needs permission.

**Stop conditions:** unknown identity or path; destination not covered by authorization; project stop
rules (an unrelated preexisting gate failure blocks a new task rather than proving that task's output
failed); workflow gates not yet satisfied; a required isolation guarantee the host cannot provide
(v1.1 — a task that requires isolation is not permission-clean when concurrent workers would share
mutable state). Check **before** any fetch, cache write, embedding call or transmission.

**Why:** fixtures S03 (local-only data, sole cloud profile → block), S17a/S17b (unknown actor / null
path → block before fetch/embedding/cache write), S09 (red-suite project stop blocks new work).

## Gate 2 — Capabilities
Check task qualification, required tools (active, not decorative), vision/input modalities, output
contract support, and context headroom against tested limits. Labels, price tier, local execution or a
model's self-reported confidence are **not** capability proof. Required tools must not be stripped;
unknown qualification is not suitability. Capability fingerprints must be present and fresh; a
missing or stale fingerprint is a Gate 2 failure (v2.0 — Host responsibility #10).

**Why:** fixtures S04 (vision + active tools both required, both missing → block), S05 (expensive
advanced label does not cure missing tools → block with explicit rejects).

## Gate 3 — Verification
Define the acceptance contract **before** work starts. Every route must have available objective
checks, or capable independent review, appropriate to the task's consequence class. A known missing
verification prerequisite before execution means **blocked, no start**; after execution, missing or
indeterminate required evidence means **unverified**; observed acceptance violations mean **failed**
(classified per plan section 7's terminal-outcome priority — recorded here as route evidence, not
decided by the router).

**Why:** fixtures S15c (verifier revision requiring an unavailable runner → invalidate cache, block),
V01-V09 (outcome-axis cases), S10 (worker's "tests passed" without observed runner evidence →
unverified, never accepted). Detailed explanation: [gate3-verification.md](gate3-verification.md).

## Gate 4 — Affordability
All mandatory work plus required verification must fit inside approved cash and resource caps, before
any reserve. Strict caps additionally require a reliable conservative billable bound and reliable host
accounting; otherwise **block automatic dispatch** (advisory uncertainty requires explicit, revised
authorization — a user's statement of uncertainty acceptance does not waive a retained cap).

Equality passes: a route is affordable when its known bound is **less than or equal to** free
allowance; call slots satisfy `used + reserved ≤ limit`; deadline requires current time **strictly
before** deadline (equality expires). Unknown or unbounded fees block a strict cap regardless of
nominal size.

**Why:** fixtures S06/S07 (unknown price/bound/accounting → block), S08 ($0.06 work + $0.05 required
review > $0.10 available → block before start), S19 (atomic reservation, uncertain charges retained),
B01/B02a/B02b (equality/expiry boundaries), S15b (stale price quote invalidates affordability).
Detailed explanation: [gate4-affordability.md](gate4-affordability.md).

## Gate 5 — Economics (delegation)
Only after all eligibility gates pass, compare candidates: prefer **direct** where suitable; delegate
one isolated, bounded unit of work only with a plausible **all-overhead** benefit (include planning,
brief/context, execution, review, repair/escalation and re-priming costs; compare against the full
direct bound, not the worker token cost alone). Every delegation must name its isolation
expectation (`worktree+branch` preferred — see SKILL.md's isolation contract) and its owner; a
delegation with no isolation path and no owner is not an eligible delegation (v1.1). A
`speculative` set counts as one delegation unit whose shared budget is a hard ceiling, and
nested delegation is admitted only when the decision sets `NestedAllowed: yes` within its
declared depth (v2.0). Detailed explanations: [gate5-economics.md](gate5-economics.md),
[speculative-mode.md](speculative-mode.md). Recommend eligible capability escalation where direct
is unsuitable; if no candidate is eligible, the route is **blocked** — do not resurrect rejected
candidates and do not fall back to a cheaper tier to avoid blocking.

**Why:** fixtures S02 (direct $0.04 beats planner $0.03 + worker $0.02 + review $0.04 = $0.09 only
when all overhead is counted), D01 (eligible, economical delegation → delegate with reserved bound),
D02 (expired worker qualification + reduced allowance → block), E01 (recommend escalation to a
qualified, affordable, available profile even though it is more expensive than the failing direct
candidate).

## Qualification, freshness and pre-dispatch binding
A recommendation is only as strong as its evidence. Before any recommendation or dispatch:

1. **Profiles** must carry an immutable identity tuple `(host-profile-id, harness, provider,
   model-id, revision, tool/output-config revision)` plus tested capability/qualification
   evidence (v1.1: the harness is part of identity, so the same decision can target different
   runtimes).
2. **Bind** every recommendation to the task/input content, workspace, authority and authorization
   revision, capability/catalog revision, verifier contract revision and price-list revision; record
   a timestamp and freshness limits.
3. **Recheck** immediately before dispatch: current permission, identity, availability, remaining
   call allowance and deadline. Changed, expired or unknown evidence invalidates the route; cache
   keys containing only content bytes are insufficient (fixtures S15a/S15b/S15c and S16: a
   whitespace-folded cache key conflates programs with different behavior).
4. Revocation always wins over a stale cache (fixture B02c); quote/deadline equality is expiry
   (fixtures B02a/B02b).
5. No host support for required identity or fresh evidence means **advisory-only** output with an
   explicit execution blocker (fixture S24) — never a claimed successful switch.

# Autonomous Host Policy — HITL only on explicit request

Status: explanatory host companion. The normative homes are [gates.md](gates.md)
and [spec-v2.md](spec-v2.md) §8.2. The user directive of 2026-10-13 changes the
default; historical risk-based human checkpoints are superseded.

## 1. Default

Run authorized tasks autonomously. Set `HumanGate` to `none` unless the user
explicitly asks for human involvement in that task or project. Store that request
with its source; a model-generated risk label or eval table is not a user request.

Risk still informs isolation and verification. Unknown permissions, missing
acceptance checks, exhausted allowances, or unsafe recovery mean `blocked`.
Produce the evidence record and stop automatically; do not manufacture an approval
question, silently weaken a gate, or transfer ownership.

## 2. HumanGate → Concrete Host Behavior

| HumanGate | Host behavior | Applies when |
| --- | --- | --- |
| `none` | Work, checks, one bounded repair, eligible merge and cleanup within authorization | Default |
| `review-before-dispatch` | Prepare the Brief and isolation; wait before launching | User explicitly requested pre-launch review |
| `review-before-merge` | Work and verify; wait before merging | User explicitly requested merge review |
| `approval-required` | Prepare evidence; wait before the named effect | User explicitly requested approval |

## 3. Autonomous lifecycle

1. Collect current identity, permission, capability, verifier, price and accounting
   inputs. Apply the five gates. A blocked route starts no worker.
2. Create the required isolation and inject the exact Brief. The filename
   `SMARTROUTER_BRIEF.json` is a Host convention, not a normative schema field.
3. The owning worker implements and runs the acceptance contract. Required checks
   run as observed commands; self-reported success is unverified.
4. A failure returns to the same owner. At most one same-profile repair total is
   available under the original allowance (R01/R02/R03); implementation, CI and
   review feedback share it. Never renew counters by restart, rename or escalation.
5. A repeated failure, no progress, expired deadline, exhausted cap, or forbidden
   effect stops automatically with a redacted `blocked` evidence package. The Host
   may request a fresh eligible routing decision using the recorded Outcome;
   it cannot launch an unpriced, unauthorized or unqualified fallback.
6. After observed acceptance and required CI, the Host performs the authorized
   merge and cleanup. A human merge checkpoint exists only on explicit request.

## 4. Executable supervisor

`tools/host_watchdog.py` wraps one command per invocation. Default exit codes:
0 successful command, 1 one corrective dispatch granted, 2 terminal automatic
stop, 3 invalid configuration. The Host consumes a repair grant exactly once.
Terminal reasons persist in the state file and refuse later launches for that task,
including when the caller no longer supplies the original stop signal.

The default terminal package has `status: blocked`, `human_requested: false`
and an empty action menu. It retains the Brief, decision, history, log and diff/PR
references. Logs are redacted before state/package persistence and before output.

`--human-requested` is supplied only from an explicit user instruction. In that
mode a terminal package has `status: needs-human` and the optional human action
menu. To enforce an explicitly requested pre-dispatch checkpoint, the Host also
passes `--gate-raised`; the command is not launched.

Timeouts stop the supervised command. Descendant process-tree cleanup, crash-safe
cash/call reservations, fresh model identity and end-to-end agent dispatch remain
Host responsibilities; a policy verdict alone does not establish those guarantees.

## 5. Class statistics

`tools/class_breaker.py` records facts per task and recomputes rates only under
the separately authorized eval protocol. `gate` defaults to `none`; a published
human gate is applied only with `--human-requested`. A statistic cannot opt a user
into HITL. Evaluation authorization and permission to spend remain separate inputs.

# SmartRouter + Isolated Workers — Working Specification v3.0 (autonomous default)

**Status:** single source of truth for the SmartRouter **v3.0 surface** — routes, isolation,
ownership, HumanGate, nesting, speculative sets, machine-readable objects, Host
responsibilities, compliance. Strictly additive over the pinned five-gate contract
([gates.md](gates.md), fixture-pinned to `docs/DEVELOPMENT_PLAN.md@d7c00f9`): where the two
overlap they agree; gate semantics remain fixture-pinned, surface semantics live here.
The skill ([SKILL.md](../SKILL.md)) is the decision procedure; this document is its complete
external contract. Per §13, later versions are strictly additive, and a Host implementing
only up to version *N* must ignore unknown fields and refuse any route it cannot enforce.

## 1. Purpose

SmartRouter is a fail-closed, deterministic routing policy for coding-agent systems.
For every coding task it decides:

- which profile (model + tools + configuration) is eligible
- whether work should be done directly, delegated to an isolated worker, explored in parallel, escalated, or blocked
- the minimum isolation strength required
- who owns the acceptance contract
- when a human must intervene

SmartRouter itself never executes code, creates worktrees, spends money, or switches models.
All enforcement, isolation, budgeting, and side-effects belong to a Host.

This document is the complete, self-contained specification of both the policy and the required Host contract.

## 2. Core Principles

1. **Fail-closed** — any unknown or missing evidence results in `blocked`. Never silent downgrade.
2. **Deterministic** — identical inputs always produce identical decisions.
3. **Advisory-only** — SmartRouter only recommends; the Host alone may act.
4. **Ownership is sticky** — all feedback returns to the current owner.
5. **Isolation is a lower bound** — Host may only strengthen isolation, never weaken it.
6. **Observed evidence only** — claims without runner logs or recorded checks are unverified.
7. **No resurrection** — a candidate rejected by any gate stays rejected for that decision.
8. **Counters never reset** — rename, restart, or profile change does not renew cash, call, or attempt budgets.

## 3. Roles

| Role                  | Responsibility |
|-----------------------|----------------|
| **SmartRouter**       | Pure decision procedure. Emits route, constraints, and machine-readable objects. |
| **Host**              | Collects inputs, enforces every decision, creates isolation, runs agents, accounts for spend, routes feedback, maintains the Outcome Ledger. |
| **Project Orchestrator** (optional) | Long-lived planning context. May request routes and spawn workers. Never owns an implementation brief. |
| **Worker**            | Owns exactly one brief from start to acceptance (or explicit escalation). Runs inside the isolation requested by SmartRouter. |
| **Human**             | Intervenes only when `HumanGate` requires it. |

## 4. Decision Model — Ordered Gates

Before any dispatch the Host collects the named inputs and asks SmartRouter to evaluate **every** candidate profile against the five gates **in strict order**. A candidate failing any gate is rejected.

**Gate 1 — Permissions / Privacy / Workflow**
- Identify authorized actor, provider, destination, data classes and effects.
- Default deny for unknown identity, path or destination.
- Read-only is **not** automatically non-disclosing.
- Project stop-rules block new work.

**Gate 2 — Capabilities**
- Task qualification, required active tools, input modalities, output contract, tested context headroom.
- Labels, price tier or self-confidence are **not** capability proof.
- Capability fingerprints must be present and fresh; missing or stale fingerprints fail this gate.

**Gate 3 — Verification**
- Acceptance contract must be defined **before** work starts.
- Required checks must be available and affordable.
- Missing prerequisite before start → `blocked`.
- Ambiguous evidence after start → unverified.
- Observed violation → failed.

**Gate 4 — Affordability**
- Conservative bound for all mandatory work **plus required verification** must fit remaining allowance.
- Equality is allowed for cash and call slots.
- Deadline requires current time **strictly before** expiry.
- Unknown or unbounded fees block any strict cap.

**Gate 5 — Economics**
- Only candidates that passed Gates 1–4 are compared.
- Prefer `direct` when suitable.
- `delegate` only for one isolated, bounded unit that shows all-overhead benefit.
- `speculative` only under high uncertainty **and** when the Host has explicitly opted in.
- Recommend escalation when direct is unsuitable.
- Empty eligible set → `blocked`.

## 5. Route Types

| Route                    | Meaning |
|--------------------------|---------|
| `direct`                 | Chosen profile performs the work itself. |
| `delegate`               | Spawn one isolated Worker that becomes the sole owner of the brief. |
| `speculative`            | Spawn a bounded parallel set of candidates; first success wins; losers are cancelled. |
| `recommend-escalation`   | No current candidate is suitable; recommend a stronger eligible profile. |
| `blocked`                | No eligible candidate exists. Report the first failing gate and reason. |

## 6. Isolation Contract

SmartRouter recommends the **minimum** isolation strength required:

| Value                   | Description |
|-------------------------|-------------|
| `none`                  | Shared working tree (only for trivial, low-blast-radius work). |
| `directory`             | Isolated directory with no shared mutable state. |
| `worktree+branch`       | Dedicated git worktree + unique branch (preferred default). |
| `ephemeral-container`   | Clean container or VM (highest isolation). |

**Host rule (normative):** the Host may only choose equal or stronger isolation. Choosing weaker isolation is a protocol violation.

Recommended branch naming: `sr/<task-id>/<short-slug>`.

## 7. Ownership & Feedback Loop

- Every `delegate` route (or the winning candidate of a `speculative` set) becomes the **Owner**.
- Verification failures, CI failures, and review comments **always** return to the current Owner.
- At most one same-profile corrective dispatch is permitted under the original allowance (plan R01/R02/R03).
- Ownership never transfers silently. If the Owner becomes ineligible, a full new SmartRouter decision is required.
- The Project Orchestrator may observe status and request new routes; it does not become Owner of an existing brief.

## 8. Adaptive Features

**8.1 Adaptive Isolation**
Isolation strength is derived from the combination of Gate 1 (permissions/privacy), Gate 3 (consequence class) and Gate 5 (economics). See table in §6.

**8.2 HumanGate**

Default `none`. A non-`none` gate requires an explicit user request for that task
or project, recorded by the Host with its source. Risk classifications, eval
recommendations, ambiguity, or failed attempts never constitute that request.
Work, observed verification, bounded repair (R01/R02/R03), and eligible host merge
proceed autonomously within existing authorization. Missing permissions,
verification, accounting, budget, or recovery capability produce `blocked` or a
terminal failure record, not an inferred approval question. The Host may re-route
an eligible bounded recovery but may not bypass any gate or renew counters.
A requested human checkpoint remains binding; autonomy is not authorization
for an effect outside the user's task.


| Value                      | Meaning |
|----------------------------|---------|
| `none`                     | Fully autonomous. |
| `review-before-dispatch`   | Human must approve the brief before the Worker is spawned. |
| `review-before-merge`      | Human must approve before acceptance or merge. |
| `approval-required`        | Explicit human authorization is required for this route. |

**8.3 Nested Delegation**
- Permitted only when SmartRouter sets `NestedAllowed: yes`.
- Parent Worker remains the Owner.
- Sub-worker receives a NestedBrief with tighter bounds and a reduced allowance
  (schema: §10.4 — bounds are checked against the parent's *remaining* allowance).
- All cash, call and attempt counters roll up to the original task.
- Default maximum depth = 1 (Host policy may raise it to 2).
- Only a speculative winner, after it becomes sole owner, may nest; nested
  speculative sets are not allowed (§8.4).

**8.4 Speculative Parallel Candidates**

```
Route: speculative
SpeculativeSet:
  candidates: [ {profile, weight?}, ... ]
  max-parallel: N
  shared-budget: { cash, calls }
  cancel-policy: first-success | budget-exhausted | all-fail
  winner-owns: true
```

Rules:
- The shared budget is a hard ceiling across the entire set.
- The first candidate that satisfies the acceptance contract becomes the sole Owner.
- Losers are cancelled; their partial results are retained only as evidence.
- Speculative mode is opt-in under any strict cash cap.
- Nested speculative sets are not allowed.

**8.5 Outcome-Aware Re-routing**
The Host may supply a `PreviousResult`. SmartRouter may then recommend continuation with a refined brief, escalation of ownership, change of isolation, or `blocked`.
SmartRouter remains stateless; the Host owns the Outcome Ledger.

**8.6 Dependency Declarations**
Workers may emit soft `blocks` / `unblocks` lists in their Result. The Host or Project Orchestrator may use them for scheduling. SmartRouter itself does not perform scheduling.

## 9. Required Output Format

Every SmartRouter decision must contain:

```
Difficulty:        <trivial | moderate | high-or-ambiguous>
Route:             <direct | delegate | speculative | recommend-escalation | blocked>
Profile:           <exact identity tuple or "none — blocked">
Isolation:         <none | directory | worktree+branch | ephemeral-container>
IsolationReason:   <short gate-derived justification>
Owner:             <orchestrator | worker | "none">
HumanGate:         <none | review-before-dispatch | review-before-merge | approval-required>
NestedAllowed:     <yes | no>
MaxNestingDepth:   <0 | 1 | 2>
Reservations:      <conservative all-in bound or "unknown/blocked">
Calls:             <used / limit>
Deadline:          <status>
Uncertainty:       <list of exact unknowns; never hide unpriced or unbounded fees>
```

When `Route` is `delegate` or `speculative`, the corresponding machine-readable object(s) defined in §10 **must** also be emitted.

When the Host cannot act on the recommendation, add:

```
Advisory: recommendation only — no dispatch performed or claimed
```

## 10. Machine-Readable Objects (Normative Schemas)

**10.1 Brief** (required for every `delegate`)

```json
{
  "objective": "string",
  "acceptance": {
    "checks": [
      { "command": "string", "expect": "string" }
    ]
  },
  "sources": ["string"],
  "permitted-effects": ["string"],
  "non-goals": ["string"],
  "isolation": "none | directory | worktree+branch | ephemeral-container",
  "branch-hint": "string",
  "allowance": {
    "cash": 0.0,
    "calls": 0,
    "deadline": "ISO-8601 datetime"
  },
  "attempts": 1,
  "stop-triggers": ["string"],
  "ownership": "worker",
  "nested-allowed": false,
  "max-nesting-depth": 1
}
```

**10.2 SpeculativeSet** (required for every `speculative` route)

```json
{
  "candidates": [
    { "profile": "string", "weight": 1.0 }
  ],
  "max-parallel": 2,
  "shared-budget": {
    "cash": 0.0,
    "calls": 0
  },
  "cancel-policy": "first-success | budget-exhausted | all-fail",
  "winner-owns": true
}
```

**10.3 Outcome / PreviousResult** (supplied by Host for re-routing)

```json
{
  "task-id": "string",
  "outcome": "accepted | verification-failed | partial | cost-overrun | cancelled | blocked | escalated",
  "evidence": {
    "checks": [
      {
        "command": "string",
        "exit-code": 0,
        "output-ref": "string"
      }
    ],
    "actual-spend": 0.0,
    "files-touched": ["string"],
    "notes": "string"
  },
  "original-brief-fingerprint": "string",
  "owner-profile": "string"
}
```

**10.4 NestedBrief** (required whenever a Worker delegates a sub-unit under
`NestedAllowed: yes`)

```json
{
  "parent-task-id": "string",
  "parent-brief-fingerprint": "string",
  "nesting-depth": 2,
  "max-nesting-depth": 1,
  "objective": "string (one narrowed sub-unit of the parent objective)",
  "acceptance": {
    "checks": [
      { "command": "string", "expect": "string" }
    ]
  },
  "permitted-effects": ["string (subset of the parent's)"],
  "non-goals": ["string (the parent's, plus no further nesting at max depth)"],
  "isolation": "none | directory | worktree+branch | ephemeral-container (>= parent's)",
  "allowance": {
    "cash": 0.0,
    "calls": 0,
    "deadline": "ISO-8601 datetime (at or before the parent's)"
  },
  "attempts": 1,
  "ownership": "parent-worker",
  "nested-allowed": false
}
```

Bound rules (checked by the Host before spawning the sub-worker, and by
`tools/conform_spec.py`):

- `allowance.cash` / `allowance.calls` fit inside the parent's *remaining* allowance
  (not its original); `allowance.deadline` is at or before the parent's deadline.
- `attempts` does not exceed the parent's remaining attempts.
- Every `permitted-effects` entry is covered by the parent's `permitted-effects`;
  `non-goals` include the parent's, plus no further nesting once
  `nesting-depth == max-nesting-depth`.
- `isolation` is at least as strong as the parent's (§6 lattice order).
- `nesting-depth` is the parent's depth + 1 (a top-level Brief is depth 1) and never
  exceeds `max-nesting-depth`; at max depth `nested-allowed` must be `false`.
- `ownership` stays the parent worker: the sub-worker reports to the parent, and the
  parent remains the Owner toward the Host. All counters roll up to the original task.

**10.5 LedgerRecord** (one auditable line per decision, dispatch, spend, outcome, or
escalation — the Outcome Ledger record format behind Host duty §11.8)

```json
{
  "task-id": "string",
  "seq": 1,
  "kind": "decision | dispatch | outcome | spend | escalation",
  "ts": "ISO-8601 datetime",
  "profile": "exact identity tuple or null",
  "counters": {
    "calls-used": 0,
    "calls-limit": 0,
    "cash-spent": 0.0,
    "cash-cap": 0.0,
    "repairs-used": 0,
    "repairs-allowed": 1
  },
  "deadline": "ISO-8601 datetime or null",
  "brief-fingerprint": "string or null",
  "detail": "string (route | request id | spend delta | escalation reason)",
  "outcome-ref": "§10.3 Outcome task-id or null"
}
```

Ledger rules: one record per event, `seq` starts at 1 per task and strictly increases;
records are append-only and never rewritten (a superseding outcome appends a new
`outcome` record and points at it via `outcome-ref`); a `dispatch` record is written
*before* sending (slot reservation, plan §8); counter fields always describe the task
totals *after* applying the event. `tools/conform_spec.py` validates records;
`tools/outcome_ledger.py` remains the §10.3 Outcome store that `outcome-ref` points at.

## 11. Host Responsibilities (Normative)

A compliant Host **must**:

1. Collect all required inputs before invoking SmartRouter.
2. Enforce every gate decision; never override a `blocked` result.
3. Create isolation at least as strong as the recommended value.
4. Inject the exact Brief (or SpeculativeSet) into each Worker's environment.
5. Account for every physical dispatch, including cancelled speculative candidates.
6. Route all verification, CI and review feedback to the current Owner.
7. Default `HumanGate` to `none`; honour a non-`none` gate only when it is backed by an explicit user request, recorded with provenance.
8. Maintain an auditable Outcome Ledger in the §10.5 record format.
9. Never reset cash, call or attempt counters by rename, restart or profile change.
10. Treat missing or stale capability fingerprints as a Gate 2 failure.

A Host **may**:

- Choose stronger isolation than recommended.
- Refuse speculative mode under strict cash caps.
- Implement additional scheduling on top of dependency declarations.
- Provide a Project Orchestrator.

## 12. Hard Prohibitions

- No dispatch on unknown permissions, identity, destination, capability, price or accounting under a strict cap.
- No empty-set resurrection.
- No required-tool stripping or silent substitution of tools or models.
- No automatic replay or provider switch after side-effects with unknown acceptance.
- No shared mutable working tree when any form of isolation was requested.
- No savings or completion claim without observed, recorded evidence.
- No ownership transfer without a fresh SmartRouter decision.

## 13. Versioning

| Version | Key additions |
|---------|---------------|
| 1.0     | Five ordered gates + basic `direct` / `delegate` / `blocked` |
| 1.1     | Isolation contract, ownership model, machine-readable Brief |
| 1.2     | Adaptive isolation + HumanGate |
| 1.3     | Nested delegation + Outcome-aware re-routing |
| 1.4     | Speculative parallel candidates |
| 2.0     | Complete surface defined by this document |
| 2.1     | NestedBrief schema (§10.4), LedgerRecord schema (§10.5), emit-validation duty (§14) |
| 3.0     | User-directed autonomous default; HITL opt-in only; automatic stops remain blocked |

Version 3.0 intentionally changes the human-intervention default under the user directive of 2026-10-13; the five eligibility gates and existing schemas remain intact. Older Hosts must not claim v3.0 behavior until they adopt this default and preserve explicitly requested gates. Additive unknown fields remain ignorable; unsupported routes must be refused.

## 14. Compliance

A system is **SmartRouter-compliant** when and only when:

- it treats this specification as the sole routing authority,
- it implements all Host responsibilities in §11,
- it never violates the hard prohibitions in §12,
- it validates every §10 object it emits (schema, enums, and bound rules such as
  §10.4 sub-allowances) and refuses routes whose objects it cannot produce or enforce
  (a 2.0 Host refuses `NestedAllowed: yes` routes rather than guessing the sub-brief),
- and it can correctly produce and consume the objects defined in §10.
